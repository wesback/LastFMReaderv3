## Summary

Build a stateless, container-friendly CLI tool (`lastfm-sync fetch`) to export Last.fm scrobble history with incremental sync capabilities. The tool supports:

- **Local NDJSON output** (default): append-only per-user scrobble files with atomic watermark persistence
- **Azure Blob Storage output** (optional): time-partitioned blobs with managed identity or SAS token auth
- **Crash-safe resumption**: watermark-based idempotent re-runs; zero duplicates
- **Rate limit compliance**: 3 QPS throttling with exponential backoff on 429/5xx
- **Production-ready**: structured logging (zap), container deployment (distroless), comprehensive testing

**Technical approach**: Go 1.22 static binary for portability; spf13/cobra for CLI; pluggable writer/watermark interfaces for flexible storage backends; Docker + GitHub Actions for build/release.

## Architecture & Design

### Component Overview

**1. CLI Layer (`cmd/lastfm-sync`)**
- Cobra-based command parser
- Command: `fetch` (primary), `show-watermark`, `set-watermark`, `version`
- Delegates to config, logging, and service layers

**2. Config Layer (`internal/config`)**
- Viper: loads from flags → env vars → config file (YAML/TOML/JSON)
- Validation: required fields (LASTFM_API_KEY, output target), auth precedence
- Resolves paths: `~/.lastfm/`, `$XDG_CONFIG_HOME`, or explicit `--state-path`

**3. Last.fm API Client (`internal/lastfm`)**
```go
type Client struct {
    BaseURL   string
    APIKey    string
    Limiter   rate.Limiter     // 3 QPS default
    Timeout   time.Duration    // 15s default
    RetryMax  int              // 5 retries
}

type Page struct {
    Scrobbles []Scrobble
    Page      int
    Total     int
    TotalPages int
}

func (c *Client) FetchPage(ctx context.Context, username string, from, until int64, pageNum, pageSize int) (*Page, error)
```
- HTTP client with custom middleware: rate limiting, retry with backoff, timeout enforcement
- Respects Retry-After header on 429
- Parses Last.fm API response; filters out "now playing" (no date)

**4. Writer Interface (`internal/writer`)**
```go
type Scrobble struct {
    Username   string                 `json:"username"`
    Artist     string                 `json:"artist"`
    Track      string                 `json:"track"`
    Album      string                 `json:"album"`
    UTS        int64                  `json:"uts"`
    MBID       *string                `json:"mbid,omitempty"`
    Source     string                 `json:"source"`
    IngestedAt string                 `json:"ingested_at"`
    Raw        json.RawMessage        `json:"raw"`
}

type Writer interface {
    WriteBatch(ctx context.Context, records []Scrobble) error
    Flush(ctx context.Context) error
    Close(ctx context.Context) error
}
```
- **LocalWriter**: buffered NDJSON append to file; fsync on flush
- **AzureWriter**: batches records → temp file → uploads to time-partitioned blob path

**5. Watermark Store Interface (`internal/watermark`)**
```go
type WatermarkStore interface {
    Get(ctx context.Context, username string) (uts int64, exists bool, err error)
    Put(ctx context.Context, username string, uts int64) error
}
```
- **FileStore**: JSON watermark file per user at `~/.lastfm/{user}.watermark`; atomic write
- **AzureStore**: blob path `{prefix}{user}.watermark`; ETag-based concurrency

**6. Rate Limiter & Retry (`internal/ratelimit`)**
```go
type Limiter struct {
    Limiter     rate.Limiter
    BackoffFunc backoff.BackOff
}

func (l *Limiter) DoWithRetry(ctx context.Context, fn func() error) error
```
- Uses `golang.org/x/time/rate` for token-bucket rate limiting
- Exponential backoff (cenkalti/backoff): 1s, 2s, 4s, 8s, max 32s
- Honors Retry-After header if present

**7. Logging (`internal/logging`)**
- Structured JSON logs (zap)
- Secret redaction: API keys, SAS tokens logged as `****last4`
- Event IDs: `fetch.start`, `fetch.page`, `fetch.write`, `watermark.update`, `retry`, `rate.limit`

### Data Flow

```
CLI parse flags → Config load/validate
  ↓
Create Last.fm Client + Writer + WatermarkStore
  ↓
Load watermark for user
  ↓
Effective lower bound = max(--since, watermark)
  ↓
Loop: Page = FetchPage(username, from, to, page_num)
  ├─ Apply rate limiting
  ├─ Retry on 429/5xx (exponential backoff)
  ├─ Filter "now playing" (no uts)
  ├─ Check short-circuit: if 0 records with uts > watermark, exit loop
  ├─ Transform to internal Scrobble + add ingested_at
  └─ WriteBatch(records) → Writer flushes per page
  ↓
After each page: Update watermark atomically
  ↓
On success: Close() → exit code 0
On error: Log + exit code 1
```

### Error Handling & Resilience

| Error | Strategy | Result |
|-------|----------|--------|
| 429 (rate limit) | Exponential backoff + retry | Transparent; logged as retry event |
| 5xx (server error) | Exponential backoff + retry | Retry up to 5 times; fail after max |
| Network timeout | Backoff + retry | Configurable via `--timeout` |
| File permission denied | Log error + exit | User fixes directory permissions |
| Azure auth invalid | Log error + exit | User provides valid credentials or fixes MSI |
| Malformed scrobble | Log warning + skip | Continue processing other records |
| Process crash mid-page | Watermark not yet updated | Rerun from last-committed watermark (idempotent) |

## Azure Blob Storage Details

### Auth Precedence

1. **DefaultAzureCredential** (recommended for Azure environments):
   - Managed Identity (Azure VMs, App Service, AKS, Container Apps)
   - Visual Studio (local dev)
   - Azure CLI login
   - Environment variables

2. **Connection String** (`AZURE_STORAGE_CONNECTION_STRING`):
   - Full connection string from Azure Portal
   - Less secure; use for development only

3. **SAS Token** (Shared Access Signature):
   - Limited-scope temporary credentials
   - Requires full container URL + token
   - Ideal for time-limited jobs

### Blob Layout

```
Container: scrobbles
├── dt=2025-10-30/
│   ├── alice-20251030-150000.ndjson
│   ├── alice-20251030-160000.ndjson
│   └── bob-20251030-150000.ndjson
├── dt=2025-10-31/
│   └── alice-20251031-120000.ndjson
└── alice.watermark (if --watermark-store azure)
```

**Path format**: `{prefix}dt=YYYY-MM-DD/{username}-YYYYMMDD-HHMMSS.ndjson`

**Benefits**:
- Immutable files (no overwrites)
- Easy partition pruning (delete old dates)
- Retry-safe: reupload same file = idempotent
- Query-friendly for data lakes (Synapse, Big Query, etc.)

### Upload Strategy

1. Write NDJSON records to temporary file on disk
2. On flush: call `azblob.Client.UploadFile(ctx, blobPath, file, &azblob.UploadFileOptions{...})`
3. Set metadata: Content-Type, tags (username, source)
4. SDK retries transient errors (3 retries default)
5. On success: delete temp file; update watermark
6. On failure: log error; temp file left for debugging; exit with error

### Security Defaults

- **Never log secrets**: API keys, SAS tokens redacted as `****last4`
- **TLS enforced**: SDK uses HTTPS by default
- **Default to Managed Identity**: Prefer DefaultAzureCredential over connection strings
- **Read-only mode**: Docker container runs with read-only filesystem (except `/data` volume for local output)

## Non-Functional Requirements

### Performance

- **Throughput**: ≥ 200 scrobbles/sec locally (bottleneck: Last.fm API 3 QPS)
- **Latency**: 10K scrobbles in < 30 seconds total (API 3+ pages/sec @ 200 recs/page)
- **Incremental re-run**: < 5 seconds (watermark read + delta sync)
- **Memory usage**: < 100MB for 100K scrobble batch in memory

### Idempotency

- Re-run same command → no duplicate records in output
- Watermark ensures monotonic progress; never regress
- Transient errors (network blips) automatically retried

### Fault Tolerance

- Crashes mid-page: watermark not updated; rerun resumes from last-committed page
- Network errors: exponential backoff + max retries; clear error on failure
- File system errors: atomic writes prevent corruption
- Azure transient errors: retry with backoff; 99% success rate

### Portability

- Single static binary: works on Linux/macOS/Windows
- No system dependencies (except CA certs for TLS)
- Container images: ghcr.io, Docker Hub compatible
- Kubernetes-native: CronJob scheduling, RBAC, Workload Identity support

### Scalability (v1 constraints, post-v1 enhancements)

- Single user per run (v1); batch mode for multi-user (v2)
- Supports up to 1M+ scrobbles per user
- Rate limit compliance: respects Last.fm 3 QPS global limit
- Azure: partition by date enables archive/retention policies
